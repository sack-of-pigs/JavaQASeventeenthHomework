# Менеджер турниров Game: Практика Java Collections Framework (List, HashMap) и CI

Учебный проект, направленный на глубокое изучение каркаса коллекций Java (Java Collections Framework). В проекте отрабатываются навыки управления списками (`List`), кастомными исключениями, а также оптимизация алгоритмов поиска элементов от линейного времени к константному за счет внедрения хэш-мап (`HashMap`). Все процессы верификации кода интегрированы в Pull Request и автоматизированы через CI.

## 🎯 Цели и задачи проекта
* **Использование Java Collections**: переход от низкоуровневых массивов к динамическим структурам данных (`ArrayList`, `HashMap`).
* **Оптимизация алгоритмов (Refactoring)**: практика рефакторинга кодовой базы — замена хранения данных со списков на ассоциативные массивы (мапы) для ускорения поиска игроков по имени с $O(N)$ до $O(1)$.
* **Управление логикой исключений**: генерация контролируемых ошибок (`NotRegisteredException`) при попытке проведения матча с незарегистрированными участниками.
* **Работа в Git-ветках**: ведение разработки в изолированной ветке `fast` с последующим оформлением Pull Request для прохождения серверных автотестов.

---

## 📦 Архитектура данных проекта

1. **Класс `Player`**: модель участника турнира (дата-класс), содержащая уникальный идентификатор `id`, имя игрока `name` и показатель его боевой силы `strength`.
2. **Класс `Game`**: центральный менеджер турнира, управляющий списком зарегистрированных участников и логикой проведения матчей.

---

## ⚙️ Реализованная функциональность и этапы оптимизации

### 1. Механика проведения турнира
Менеджер `Game` предоставляет два ключевых интерфейса:
* **`register(Player player)`**: добавляет участника в пул турнира. Первоначально игроки сохранялись во внутреннем списке `List<Player>`, затем архитектура была переведена на `HashMap<String, Player>`, где ключом выступает имя игрока.
* **`round(String playerName1, String playerName2)`**: запускает соревнование между двумя игроками по их именам.
  * Если хотя бы один из участников не найден в системе, выбрасывается кастомная ошибка `NotRegisteredException`.
  * Победитель определяется сравнением показателей `strength`. Метод возвращает `1` (победа первого), `2` (победа второго) или `0` (ничья).

### 2. Оптимизация в ветке `fast` (HashMap)
Для закрепления навыков работы с ассоциативными массивами в ветке `fast` была проведена модернизация: прямой перебор списка циклом для поиска игрока по имени был заменен на мгновенное извлечение объекта из `HashMap` по ключу-строке, что кардинально повысило производительность приложения.

## 🧪 Тест-дизайн и верификация (JUnit 5)

В тестовых классах реализовано полноценное Unit-тестирование, покрывающее **100% путей выполнения кода (Branch Coverage)** по счетчику JaCoCo.

### Основные сценарии проверок:
* **Позитивные сценарии матчей:**
  * Победа первого игрока (сила игрока 1 > силы игрока 2).
  * Победа второго игрока (сила игрока 1 < силы игрока 2).
  * Результат ничьей (силы участников абсолютно равны).
* **Тестирование исключительных ситуаций:**
  * Генерация `NotRegisteredException`, если не зарегистрирован первый игрок.
  * Генерация `NotRegisteredException`, если не зарегистрирован второй игрок.
  * Генерация `NotRegisteredException`, если в системе отсутствуют оба участника матча.

Полный цикл сборки, статического анализа и выполнения тестов запускается через терминал:
```bash
mvn clean verify
```
*Сборка гарантированно завершается со статусом `BUILD SUCCESS`, а на GitHub Actions в рамках созданного Pull Request загорается зеленая галочка.*
